# ZeroTier system KeyStore instrumented verification

The offline JVM suite (`tests/ZeroTierAndroidStoreTest.java`) runs against a
synthetic JCE provider. That proves the storage and review semantics, not the
platform keystore. This directory runs the **same production code** against the
real `AndroidKeyStore` provider of an API 35+ device or emulator.

## What makes it a system run

* No provider is registered. The test asserts that `Security.getProvider("AndroidKeyStore")`
  resolves to a provider loaded by the same class loader as the platform classes
  (`android.os.Build`), not by the application class loader. A provider
  registered by the test would arrive through the application loader, so JCA
  must pick the platform implementation on its own — exactly as inside a
  shipped app.
* `AndroidZeroTierEnvelope` and `ZeroTierDeviceStoreCore` are compiled
  unmodified from `android-production-sources.txt`. The evidence JSON records
  their SHA-256, so the run is bound to the manifest-listed sources.
* The identity is synthetic (`IdentityFactory` / `NativeOwner` are interfaces
  of `AndroidZeroTierDeviceStore`), so no Rust `.so` and no native identity
  engine are needed.

## Cases

| Case | Assertion |
|------|-----------|
| `systemProviderActive` | the platform provider is present and comes from the boot classpath |
| `createStoresEncryptedRecord` | the record on disk is the 374-byte `HZD1` record, the 270 identity bytes never appear in it, the key lives in the system keystore, `getEncoded()` is `null` (non-exportable) |
| `freshInstanceReadsBackIdentity` | a new store instance reads the same handle and instance id without regenerating, and the decrypted identity matches the generated bytes |
| `tamperUnreadableTwoStepDiscard` | one flipped ciphertext byte makes the record unreadable, a fresh instance cannot begin a discard, the review is bound to the instance that authenticated the handle, the confirmed discard removes the identity and the key, and the review cannot be reused |
| `forgetExactLocksToInstance` | `forgetExact` with a wrong instance id is refused and leaves the record installed, the exact instance id removes the identity, the alias is gone and no recovery marker remains |

The two envelope negatives (duplicate alias, wrong AAD) run against the real
system key as part of the same case sequence.

## Running it

```sh
bash validation/network-profiles/native/android/tests/run-zerotier-keystore-instrumented.sh \
  --sdk "$ANDROID_HOME" --serial emulator-5554 --output /tmp/zerotier-keystore
```

The script compiles the production slice against the real `android.jar`, dexes
and signs a self-targeting instrumented APK without Gradle, installs it, runs
`am instrument` and writes `zerotier-android-keystore.json` plus the raw
instrumentation output into the output directory. CI runs it on the disposable
API 35 AVD from `validation/remote-harness/with-android-emulator.sh`.

## Evidence fields

| Field | Source |
|-------|--------|
| `androidAbi` | measured `Build.SUPPORTED_ABIS[0]` |
| `androidSdkInt` | measured device API level |
| `fakeAndroidKeyStore` | always `false`; the provider is the platform one |
| `keyStoreProviderClass` | the measured provider class name |
| `encryptedAtRest`, `nonExportableKey`, `freshReaderMatched`, `identityDigestMatched`, `wrongAadRejected`, `tamperRejected`, `wrongInstanceRejected`, `explicitlyRemoved`, `keyStoreEmpty` | the assertions above |
| `hardwareBacked` | measured `KeyInfo.isInsideSecureHardware()`; `null` when the platform does not answer |
| `hardwareIsolationClaimed` | always `false` |

## Boundary

An emulator runs a **software KeyMint**. This run proves the platform provider
path and the storage semantics; it cannot prove hardware isolation, TEE or
StrongBox backing, the behaviour of a real lockscreen, or a real process
restart. `hardwareIsolationClaimed` stays `false` for that reason. A physical
device is required for those conclusions.

## Why this is not a Gradle source set

Both shells generate their Android projects at build time
(`validation/flutter/tool/ci.py`, `validation/tauri/scripts/wire-android.py`)
and neither keeps a checked-in Gradle project. Adding `connectedDebugAndroidTest`
to them would mean editing both generators and building the full apps for the
emulator ABI. This standalone APK compiles the same manifest-listed production
sources directly, so the verification stays runnable without Gradle and without
touching either shell.
